# Mopl API 계약

이 디렉터리는 제공된 프로토타입 명세와 팀이 실제 구현에 사용할 합의 명세를 분리해서 관리합니다.

## 파일

- `reference/provided-openapi.json`: 프로토타입에서 제공된 OpenAPI 3.1 원본입니다. 비교 기준이므로 수정하지 않습니다.
- `mopl-api.yaml`: 팀이 합의한 요청·응답 규칙을 반영한 구현 기준입니다.

프로토타입 원본의 SHA-256은
`3C9725909B44B3D3FC562F3D4A7551D215F9D0513A13B26143B2E5FAAB2943E1`입니다.

## 합의본에 반영한 항목

- `lastestMessage`를 `latestMessage`로 바로잡았습니다.
- 새 대화에는 메시지가 없으므로 `latestMessage`는 필수 필드로 유지하되
  값으로 `null`을 허용했습니다.
- 사용자 잠금 필드를 `locked`로 통일했습니다.
- 콘텐츠 정렬값 `rate`를 `rating`으로 통일했습니다.
- 플레이리스트 정렬값 `subscribeCount`를 `subscriberCount`로 통일했습니다.
- 새 리소스 생성은 `201`, 기존 리소스를 반환하는 멱등 요청은 `200`,
  본문 없는 상태 변경과 삭제는 `204`로 구분했습니다.
- 팔로워 수를 `{ "count": number }` 형태의 객체로 감쌌습니다.
- 콘텐츠 수정 요청을 `multipart/form-data`로 바로잡았습니다.
- 시청 중인 세션이 없을 때 `204`를 반환하도록 명시했습니다.
- 공통 오류 응답에 `errorCode`를 포함했습니다.
- 요청을 거절해야 하는 리소스 충돌은 `409 Conflict`로 구분했습니다.
- 알림을 삭제하지 않고 읽은 시각을 보존할 수 있도록 `readAt`을 추가했습니다.
- 마지막 페이지의 `nextCursor`와 `nextIdAfter`는 `null`일 수 있도록 명시했습니다.
- 조회 요청은 JWT, 변경 요청은 JWT와 CSRF가 필요하도록 표시했습니다.
  회원가입·로그인·비밀번호 재설정·토큰 재발급은 CSRF만 필요하며,
  CSRF 토큰 조회는 인증 없이 호출합니다.

## 409 Conflict 적용 기준

`409`는 단순히 같은 요청이 반복됐다는 이유로 반환하지 않습니다.
서버의 현재 리소스 상태 때문에 요청을 그대로 처리할 수 없을 때만 사용합니다.

- 중복 이메일로 회원가입: `409`
- 같은 사용자가 같은 콘텐츠에 리뷰를 다시 작성: `409`
- 중복 팔로우: `200`과 기존 `FollowDto` 반환
- 이미 존재하는 사용자 간 대화 생성: `200`과 기존 `ConversationDto` 반환
- 중복 구독·플레이리스트 콘텐츠 추가: `204`
- 자기 자신 팔로우나 잘못된 평점처럼 요청 값 자체가 잘못된 경우: `400`

회원가입과 리뷰 구현에서는 중복 검사나 데이터베이스의 고유 제약 위반을
`BusinessException(ErrorCode.CONFLICT)` 또는 같은 `409` 상태를 사용하는
도메인 전용 오류 코드로 변환해야 합니다. 고유 제약 예외가 그대로 `500`으로
처리되지 않도록 합니다.

## 아직 확정하지 않은 항목

다음 항목은 팀 합의 후 별도의 작업에서 계약과 구현을 함께 변경합니다.

- 알림 읽음 처리의 정확한 HTTP 메서드와 경로
- 팔로우하지 않은 경우와 대상 사용자가 존재하지 않는 경우의 응답 구분
- 본인 조회용 `/api/users/me` 추가 여부
- 각 엔드포인트의 세부 오류 응답 범위

계약 변경의 논의 기록은
[Swagger 계약 계획 및 합의 기록](https://app.notion.com/p/Mopl-Swagger-API-3abd250dfa26810ca57bc5d184485bfa)에서 관리합니다.
