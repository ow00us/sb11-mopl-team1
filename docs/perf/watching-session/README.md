# 시청 세션·같이 보기 — k6 부하 테스트 결과

## 측정 환경

- **대상 Git SHA**
    - backend: `c43265484a151d120fa29ba27764c183a9eb9d31` (main)
    - frontend: `260b09f450de40596ecead19d01b866881273484` (main)
- **이미지**: ECR 접근 권한이 없어 위 커밋을 로컬에서 재빌드 (`linux/amd64`). Apple Silicon(arm64) 호스트에서 에뮬레이션으로 실행됨.
    - 절대적인 p95/max 수치는 실제 운영 서버(x86_64 EC2)보다 나쁘게 나올 수 있음. **조건 간 상대 비교** 위주로 해석할 것.
- **구성**: `docker-compose.prod.yml` + `docker-compose.perf-override.yml`을 별도 로컬 환경에 기동 (운영 서버 아님)
    - `IMAGE_STORAGE_ENABLED=false`, `KAFKA_TOPIC_VERIFY=false`로 우회 — 둘 다 watch/chat 경로와 무관
- **데이터 규모**: 계정 300개(`k6-watch-0`~`k6-watch-299`), 콘텐츠 1개(고정 UUID)
- **설정값**: `WATCHING_SESSION_CONTENT_EXISTENCE_CACHE_TTL` 30s(on) / 1ms(off 근사, 하한 제약으로 0 불가)
- **시나리오**: CONNECT → watch·chat 구독 → heartbeat(20s 주기) → 채팅 발신(7~10s 랜덤) → 2분 30초 유지
- **반복**: 조건당 3회 실행, 표에 기록된 값은 정상 회차만 반영 (아래 "회차 제외 사유" 참조)

## 회차 제외 사유

로컬 macOS 환경에서 300 VU 동시 접속 시 일부 회차의 에러율이 0%에서 최대 100%까지 불규칙하게 튀는 현상이 관찰됨. 서버 측 드롭 카운터는 전 회차 0으로, 유량 제한이 원인이 아님. 파일 디스크립터 등 **클라이언트(k6 실행 호스트)의 리소스 한도로 추정**되나 이번 환경에서 확정 짓지는 못함.

- **A(1인스턴스·캐시 on)**: 3회 중 2회(run1, run2, 에러율 0%)만 채택. run3(에러율 100%)은 이상치로 제외.
- **B(1인스턴스·캐시 TTL 1ms)**: 3회 중 2회(run2, run3, 에러율 0%)만 채택. run1(에러율 54%)은 이상치로 제외.
- **C(2인스턴스)**: 3회 전부 에러율이 불안정(20%/0%/42%)하여 하나만 고르지 않고 **3회 전부 기록**, 별도 한계로 명시 (아래 "2인스턴스 조건 참고" 참조).

## 2인스턴스 조건 참고 (한계 명시, 후속 조치 없음)

2인스턴스 조건은 3회 모두 에러율이 불규칙했다(19.9% / 0% / 41.8%). 서버 측
드롭 카운터는 두 인스턴스 모두 0으로, 유량 제한이나 서버 처리 한계는 아니다.
로컬 macOS 환경(Apple Silicon 위 amd64 에뮬레이션, 두 backend 컨테이너의
CPU 공유)의 영향으로 추정되나, 원인을 확정하지 못했다.

프로젝트 일정상 스테이징 등 별도 환경에서의
재검증 계획은 없다. 이 수치는 1인스턴스 대비 2인스턴스가 명확히 나쁘지
않다는 정도의 참고 자료로만 사용하고, 정확한 2인스턴스 포화점 비교의
근거로는 쓰지 않는 것을 권장한다.

## 결론

- 이 구성(로컬 재현 환경, amd64 에뮬레이션)에서 1인스턴스 기준 **300명 동시 접속까지 에러율 0%, watch 구독 ack p95 약 40~80ms, 채팅 전달 p95 약 50~90ms**로 안정적으로 관찰됨.
- 그 이상 규모에서의 정확한 포화점은 이번 로컬 측정 환경의 한계(에뮬레이션, 클라이언트 리소스 한도)로 인해 확정하지 못함. 운영과 동일한 x86_64 환경에서의 재측정이 필요.
- 드롭 카운터가 전 조건·전 회차 0으로 나온 것은, 관찰된 지연·에러율 변동이 유량 제한 설정이 아니라 다른 요인(클라이언트/환경)에서 비롯됨을 시사함.
- 콘텐츠 존재 캐시 on/off 비교는 이번 데이터 규모(콘텐츠 1개)에서 유의미한 차이를 보이지 않음 — 콘텐츠 수가 많은 환경에서 재검증 권장.

## 실행 방법

`k6/README.md` 참조. 요약:

```bash
# 사전 조건: docker-compose.prod.yml + docker-compose.perf-override.yml 기동, perf.env 준비
k6 run --env BASE_URL=http://localhost:8080 --env COUNT=300 k6/seed-users.js

export CONTENT_ID=<고정 콘텐츠 UUID>
export ACCOUNT_COUNT=300
export PEAK_VUS=300
./run_all.sh
./collect_results.sh
```

원본 k6 raw 출력(`results/*.json`)은 용량 문제로 저장소에 포함하지 않음. 요약본(`results/*-summary.json`)과 드롭 카운터 스냅샷만 포함.
