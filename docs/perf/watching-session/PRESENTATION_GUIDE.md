# 시청 세션 부하 테스트 발표 구성 제안

## 발표의 중심 문장

> 300 VU 도달 자체는 성공했지만, 2인스턴스 조건은 같은 설정에서 67.78% / 0% / 0.19%로 갈렸다. 분산 처리는 확인했으나 반복 안정성과 원인은 확인하지 못했다.

이번 발표의 주인공은 “300명 처리”가 아니라 **잘못된 측정을 폐기하고도 남은 간헐적 붕괴**다. 평균이나 가장 좋은 회차로 결론을 만들지 않고, 측정 계약을 어떻게 바로잡았는지와 아직 알 수 없는 범위를 함께 보여 주는 편이 설득력이 높다.

## 권장 슬라이드 5장

### 1. 처음 얻은 수치를 그대로 믿을 수 없었다

**슬라이드 제목**

> 성능 문제를 찾기 전에 측정 문제부터 발견했다

**화면에 둘 내용**

- 초기 C 오류율: `19.9% / 0% / 41.8%`
- 그러나 gateway 우회, 빈 Prometheus 파일, TTL 미적용, 오류 분모 불일치
- 결론: 초기 수치와 “drop 0” 판정 폐기

**시각화**

`k6 → backend-a`로 잘못 연결된 초기 경로와 `k6 → gateway → backend-a/b` 최종 경로를 좌우로 비교한다. 초기 수치에는 회색 취소선을 넣고 최종 측정으로 화살표를 연결한다.

**발표 대본**

> 처음에는 2인스턴스 오류율이 0에서 42% 사이로 흔들린다고 봤습니다. 그런데 실행 경로를 확인하니 k6가 gateway를 거치지 않았고, 빈 메트릭 파일을 drop 0으로 읽고 있었습니다. 숫자를 보완해서 설명하는 대신 이 결과 전체를 폐기했습니다.

### 2. 세션 성공의 정의를 다시 썼다

**슬라이드 제목**

> 연결 성공이 아니라 실제 사용 흐름의 성공을 측정했다

**화면에 둘 내용**

`CONNECTED → 자기 JOIN → 고유 chat 발신 → 자기 echo 수신`

- 과거 chat backlog는 live 지연에서 제외
- warmup 20과 measure 540 분리
- 실제 활성 VU `max=300` 확인
- summary에서 token 제거, manifest와 SHA256 저장

**시각화**

네 단계 흐름을 가로로 두고 각 단계 아래에 실패 시 watch/chat/전체 오류가 한 번만 기록된다고 표시한다. backlog는 옆의 별도 박스로 분리한다.

**발표 대본**

> WebSocket이 열렸다는 이유만으로 성공으로 보지 않았습니다. 자기 사용자의 JOIN과 자신이 보낸 고유 채팅이 실제로 돌아오는 것까지 확인했습니다. 과거 채팅 재생은 실시간 지연에서 뺐고, warmup과 본 측정도 나눴습니다.

### 3. 같은 2인스턴스 조건이 한 번만 크게 무너졌다

**슬라이드 제목**

> A·B는 0%, C는 67.78% / 0% / 0.19%

**그래프 데이터**

| 조건 | run1 | run2 | run3 |
|---|---:|---:|---:|
| A 1인스턴스·TTL 30s | 0 | 0 | 0 |
| B 1인스턴스·TTL 1ms | 0 | 0 | 0 |
| C 2인스턴스·TTL 30s | 67.78 | 0 | 0.19 |

**시각화**

평균 막대그래프 대신 조건별 세 점을 찍는 dot plot을 사용한다. y축은 오류율 0~70%, C run1만 빨간색으로 표시한다. C 평균 22.65%는 보조 텍스트로만 두고 대표값처럼 보이게 하지 않는다.

**보조 지연 데이터**

| 조건 | chat p95 run1/run2/run3 |
|---|---:|
| A | 39 / 52 / 64ms |
| B | 26 / 27 / 37ms |
| C | 44.64s / 33ms / 34ms |

chat p95는 구독 뒤 실제 수신되어 기록된 테스트 형식의 live fan-out 메시지 분포다. 관측되지 않은 실패에 timeout 값을 대신 넣지 않았고 자기 echo만의 지연도 아니므로, 오류율과 같은 화면에서 보조 지표로만 제시한다. 이후 공통 오류로 최종 실패한 세션의 앞선 표본은 남을 수 있다. C run1과 나머지 값의 차이가 매우 크므로 로그 축을 사용하거나 C run1을 별도 callout으로 뺀다. 일반 선형축 막대그래프는 A/B/C2/C3을 보이지 않게 만든다.

**발표 대본**

> 최종 결과에서 A와 B는 measure 구간 세 번 모두 오류가 없었습니다. C는 한 번 67.78%가 실패했고 다음 두 번은 0%와 0.19%였습니다. 그래서 2인스턴스가 항상 실패한다고도, 안정적이라고도 말할 수 없습니다. 문제는 평균 성능이 아니라 반복할 때 간헐적으로 전체가 무너진다는 점입니다.

### 4. C run1에서 여러 서버 신호가 함께 증가했다

**슬라이드 제목**

> 붕괴는 확인했지만 최초 원인은 아직 분리하지 못했다

**화면에 둘 표**

| 지표 | C run1 | C run2 | C run3 |
|---|---:|---:|---:|
| measure 오류율 | 67.78% | 0% | 0.19% |
| Hikari timeout | 920 | 13 | 14 |
| rate-limit drop | 594 | 0 | 0 |
| chat p95 | 44.64s | 33ms | 34ms |

**옆에 둘 제한 문장**

- C1 drop: chat-send 444, heartbeat 150, subscribe 0
- Hikari timeout 920 > 실패 세션 366
- relay publish failure 0, non-self discard 0
- 상관은 관찰했지만 인과 순서는 모름

**발표 대본**

> 실패한 회차에서는 DB 커넥션 획득 timeout 920건과 rate-limit drop 594건이 함께 늘었습니다. 그렇다고 둘 중 하나를 원인으로 확정할 수는 없습니다. 서버 카운터에는 세션별 시간 상관이 없고 watch와 chat 세부 오류도 공통 오류를 공유합니다. 현재 결론은 여러 신호가 같은 회차에 동반됐다는 데까지입니다.

### 5. 이번 PR이 확정한 것과 다음 실험

**슬라이드 제목**

> 300 VU 수행은 완료했지만 안정 용량 인증은 보류한다

**확정한 것**

- 실제 활성 VU 300 도달
- C가 두 backend에 약 50:50으로 분산
- 양방향 relay 동작, 명시적 publish 실패 0
- C의 반복 안정성 미확보

화면 각주에는 `측정 대상: 기존 PR에 기록된 main SHA(c4326548), 최신 develop 아님`을 둔다.

**다음 실험**

1. k6를 별도 호스트로 분리
2. Hikari·PostgreSQL·CPU·Redis drop을 1초 시계열로 저장
3. backend ID와 세션 ID가 있는 오류 로그 보존
4. rate limiter, Hikari pool, 인스턴스 수를 한 변수씩 변경
5. cold-start와 warmed capacity 실험 분리

**발표 대본**

> 이번 PR은 300 VU를 처리할 수 있다고 증명한 PR이 아닙니다. 실제 분산 경로에서 한 회차가 크게 붕괴한다는 사실을 재현하고, 그 현상을 다시 검증할 수 있는 측정 기반을 만든 PR입니다. 다음 단계에서는 시간축과 변수를 분리해 원인을 좁혀야 합니다.

## 60초 요약 대본

> 초기에는 2인스턴스 오류율이 0에서 42%까지 흔들린다고 봤지만, gateway 우회와 빈 메트릭 파일 등 측정 오류를 발견해 결과를 폐기했습니다. 자기 JOIN과 자기 채팅 echo를 성공 조건으로 넣고, warmup과 measure를 분리한 뒤 A/B/C를 각각 세 번 다시 실행했습니다. A와 B는 measure 오류가 모두 0%였고, C는 67.78%, 0%, 0.19%로 갈렸습니다. 실패한 C run1에서는 Hikari timeout 920건과 rate-limit drop 594건이 함께 증가했고, 기록된 live fan-out 표본의 chat p95는 44.64초였습니다. C 부하가 두 backend에 실제 분산됐고 relay의 명시적 실패는 없었지만, 어느 서버 신호가 최초 원인인지는 아직 알 수 없습니다. 따라서 300 VU 도달은 확인했으나 안정 용량이라고 주장하지 않고, 2인스턴스의 간헐적 붕괴를 후속 원인 분리 실험으로 넘기는 것이 이번 결론입니다.

## 예상 질문과 답변

### 왜 warmup 오류를 본 측정에서 뺐나?

warmup을 숨긴 것이 아니라 별도 표로 보존했다. measure 시나리오의 ramp 결과와 cold-start 진단을 섞지 않기 위해 지표를 분리했다. A/B에서는 warmup 20/20 실패와 Hikari timeout 20건이 매번 함께 나타났으므로 cold-start 문제도 별도 후속 과제다.

### C가 정말 두 인스턴스에 분산됐나?

C2 publish 비중은 50.38%/49.62%, C3은 51.42%/48.58%였다. 양방향 상대편 delivered도 교차 확인했고 publish failure와 non-self discard는 0이었다.

### 그러면 rate limiter가 원인인가?

C1에서 drop 594건이 오류와 함께 발생했으므로 원인 후보에서 제외할 수 없다. 다만 서버 카운터에는 세션별 시간 상관이 없고 DB timeout과 연결 지연도 동시에 증가했다. 현재 증거로 단독 원인을 특정할 수 없다.

### relay 2건 차이는 메시지 유실 아닌가?

before 스크레이프가 두 backend에서 약 432ms 차이로 수행되어 baseline이 2건 어긋났다. 종료 누적값은 발행과 전달이 4,924/4,924로 같고 명시적 실패도 0이었다. 집계 허용치는 `max(5건, 해당 방향 발행·전달 최대값의 0.5%)`다. 이 자료는 relay 동작을 확인하지만 무손실을 보증하지는 않는다.

### 300 VU를 지원한다고 말할 수 있나?

말할 수 없다. 300 VU 도달은 실행 사실이며 C run1의 67.78% 오류 때문에 안정 용량 인증은 실패했다. 또한 k6와 서버가 같은 호스트를 사용해 운영 포화점으로 일반화할 수 없다.

### 현재 develop도 같은 결과인가?

이번 재검증은 기존 PR이 기록한 `main` 대상 SHA를 같은 조건으로 다시 빌드해 수행했다. PR 브랜치나 최신 `develop` 애플리케이션의 성능 결과는 아니며, 그 판단에는 새 이미지와 새 측정 ID로 전 조건을 다시 실행해야 한다.
